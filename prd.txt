# Telegram Personal Music Cloud

### TPMC — Personal Music Storage, Indexing & Retrieval System

**Version:** 2.0
**Status:** Production Architecture Specification
**Target:** Personal / Single-User System
**Primary Runtime:** Python + Telethon
**Hosting:** Render Free Web Service
**Storage Backend:** Private Telegram Channel
**Repository:** Private GitHub Repository
**Development Environment:** Antigravity

---

# 1. Product Definition

## 1.1 Product Name

**Telegram Personal Music Cloud (TPMC)**

TPMC is a personal music-management system that uses a private Telegram channel as the durable media repository and a Python service as the indexing, search, command, and delivery layer.

The system is designed for one authorized owner rather than public multi-user operation.

---

# 2. Critical Architecture Principles

TPMC MUST follow these principles:

1. **Telegram is the media source of truth.**
2. **Render filesystem is never treated as permanent storage.**
3. **No music file is permanently stored on Render.**
4. **No large media file is downloaded to Render unless absolutely required.**
5. **The system should forward Telegram media whenever possible instead of downloading and re-uploading it.**
6. **The application must survive Render restarts.**
7. **The application must tolerate Render cold starts.**
8. **The application must tolerate Telegram rate limits and FloodWait conditions.**
9. **Every long-running operation must be resumable.**
10. **Every command must be bounded to prevent accidental resource exhaustion.**
11. **The bot must reject unauthorized users.**
12. **Secrets must never exist in Git.**
13. **A Render Free instance must be treated as disposable.**
14. **The system must not depend on a fake keep-alive server to remain permanently active.**
15. **The application must explicitly communicate free-tier limitations to the owner.**

---

# 3. Important Constraint Corrections

## 3.1 Render is NOT a guaranteed 24/7 host

Render Free services can spin down after 15 minutes without inbound traffic and may take approximately a minute to wake up.

The service may also restart independently.

Therefore:

### Forbidden assumption

```text
Render Free = permanently running server
```

### Correct model

```text
Render Free
     │
     ├── Running
     │
     ├── Idle
     │
     ├── Suspended
     │
     └── Cold Start
             │
             ▼
        Application Boot
             │
             ▼
        Telegram Reconnect
             │
             ▼
        Ready
```

The application must therefore be **restart-safe**, not merely "always running."

Example:

```text
Private Channel
│
├── Song A
│   ├── Artist: A
│   ├── Album: Album X
│   ├── Genre: Rock
│   └── Tags: #rock #favorite
```

The application does NOT become the storage provider.

Telegram remains the storage layer.

# 6. Dual Telegram Identity Architecture

This is one of the most important changes.

## 6.1 Bot Account

Used for:

* `/start`
* `/help`
* `/search`
* `/download`
* `/library`
* `/status`
* `/cancel`
* progress messages
* user interaction

## 6.2 User Account / MTProto Session

Used for:

* reading the private storage channel
* scanning historical messages
* accessing media metadata
* retrieving messages
* performing operations unavailable or unsuitable through the Bot API

This separation makes the system substantially more robust.

TPMC is a personal system.

It MUST NOT behave as an unrestricted public Telegram bot.

Every command must validate:

```text

```

If unauthorized:

```text

```

No channel information should be exposed.

No commands should execute.

No media should be sent.

# 15. Indexing Strategy

The original design scans the entire channel for every `/download` request.

That is inefficient.

Example:

```text
/download #rock

→ scan 20,000 messages
→ inspect each message
→ send matches
```

This does not scale well.

Instead:

```text
Startup
   ↓
Load lightweight index
   ↓
Detect new channel messages
   ↓
Update index
   ↓
User searches
   ↓
Search index
   ↓
Retrieve Telegram messages
```

---

# 16. Free-Tier Persistence Strategy

Because Render Free storage is ephemeral, TPMC MUST NOT depend on a local SQLite database as the permanent source of truth.

The system should be able to reconstruct its index from Telegram.

Therefore:

```text
Telegram
    ↓
Rebuild Index
    ↓
Memory
```

If the process restarts:

```text
Restart
  ↓
Index missing
  ↓
Rebuild from Telegram
  ↓
Ready
```

---

# 17. Index Rebuild Strategy

Never blindly perform a full expensive scan on every startup.

Use:

```text
FAST BOOT
   ↓
Bot available
   ↓
Background indexing
   ↓
Incremental reconstruction
```

During indexing:

```text
/status
```

should report:

```text
Library status

Indexed: 8,420
Scanned: 10,000
Remaining: 2,000
Status: Indexing
```

# 20. Download / Delivery Architecture

The word "download" is misleading.

The backend should primarily perform:

```text
Telegram message
      ↓
Forward / send media
      ↓
Owner DM
```

rather than:

```text
Telegram
   ↓
Render
   ↓
temporary file
   ↓
Render upload
   ↓
Telegram
```

The second architecture wastes Render bandwidth and memory.

---

# 21. Large File Handling

The application MUST detect file size before attempting delivery.

Conceptual logic:

```text
File detected
    ↓
Check size
    │
    ├── Supported
    │      ↓
    │    Deliver
    │
    └── Unsupported
           ↓
       Don't retry forever
           ↓
       Explain limitation
```

The Bot API currently documents a 50 MB sending limit for bots. Therefore the PRD must NOT claim that a bot can reliably DM every 2 GB Telegram file.

If large-file delivery is required, the implementation should use the MTProto architecture where technically appropriate and validate actual Telegram limits during integration testing.

---

# 22. Delivery Modes

TPMC should support:

### Mode A — Forward

Preferred.

```text
Storage Channel
       ↓
Forward
       ↓
Owner DM
```

Advantages:

* no local file
* lower Render resource usage
* faster
* less bandwidth pressure

### Mode B — Telegram-side copy/send

Used where forwarding semantics are undesirable.

### Mode C — Download/re-upload

Last resort only.

This mode should be disabled by default.

---

# 23. Bulk Download Protection

Never allow:

```text
/download_all
```

to blindly send thousands of files without limits.

Instead:

```text
/download_all
```

should respond:

```text
Your library contains 8,420 tracks.

This operation will send 8,420 messages.

Use:

/download_all confirm
```

Then:

```text
/download_all confirm
```

starts the job.

Bulk delivery must be chunked.

Example:

```text

1–25

Batch 2
26–50

Batch 3

```

The exact batch size should be configurable.

# 25. Rate Limiting

Never assume:

```text
sleep(1.5)
```

is sufficient protection.

Telegram may return:

```text
FloodWait
429
network timeout
connection reset
```

The system must handle Telegram-provided wait durations dynamically.

Conceptual algorithm:

```text
send message
    ↓
success → continue

FloodWait
    ↓
read server wait duration
    ↓
wait
    ↓
retry

temporary network failure
    ↓
exponential backoff
    ↓
retry

permanent failure
    ↓
record failure
    ↓
continue job
```

Telegram's own bot documentation also warns about per-chat message-rate limitations.

---

# 29. Resume Support

If Render restarts during:

```text
/download_all
```

the operation must not corrupt the system.

At minimum:

```text
Job interrupted.

Render restarted.

Please run:
 /download_all resume
```

A stronger implementation can maintain lightweight job state externally or encode enough state to reconstruct progress from Telegram message IDs.

---

# 30. Duplicate Protection

The system must avoid accidentally sending duplicate tracks during retries.

Track identity:

```text
channel_id + message_id
```

Before delivery:

```text
already completed?
      │
      ├── YES → skip
      │
      └── NO → send
```

# 32. Retry Policy

Never use infinite retries.

Example conceptual policy:

```text
Attempt 1
Attempt 2
Attempt 3
       ↓
Failure
       ↓
Record error
       ↓
Continue
```

FloodWait is special:

```text
FloodWait(n)
       ↓
wait n seconds
       ↓
retry
```

# 42. Render Free-Tier Reality

The system must explicitly tolerate:

```text
15-minute idle spin-down
Cold starts
Instance restarts
Ephemeral filesystem
Limited CPU
Limited RAM
Outbound bandwidth limitations
750 monthly instance hours
```

Render documents these limitations for Free services.

Therefore the application cannot promise:

```text
24/7 guaranteed uptime
zero cold starts
unlimited bandwidth
unlimited compute
zero downtime
```

---

# 43. Keep-Alive Design

Do NOT implement:

```text
while True:
    requests.get(my-render-url)
```

inside the application.

That is circular and does not solve the actual free-tier lifecycle problem.

External traffic may wake a sleeping service, but the application itself should remain correct when Render suspends it.

# 49. Graceful Shutdown

When Render terminates the process:

```text
SIGTERM
   ↓
Stop accepting new jobs
   ↓
Finish safe current operation if possible
   ↓
Disconnect Telegram
   ↓
Close HTTP server
   ↓
Exit
```

Do not abruptly kill running coroutines.

Render supports configurable shutdown delay for services, so graceful termination should be part of the design.

# 55. Duplicate Tracks

Duplicates must not crash indexing.

```text

```

for storage identity.

---

# 56. Memory Management

Never load the entire channel media into memory.

Bad:

```text
all_messages = list(iter_messages(...))
```

Preferred:

```text
stream messages
process one
discard temporary object
continue
```

---

# 57. Concurrency

Do not create hundreds of simultaneous Telegram operations.

Use a bounded queue:

```text
MAX_CONCURRENT_OPERATIONS = small fixed number
```

For a single-user personal application, conservative concurrency is preferable to aggressive throughput.

---

# 58. Backpressure

If the owner requests:

```text
/download_all
```

while another large job is running:

```text
Reject / queue second job
```

Do not run unlimited jobs simultaneously.

---

# 59. Command Collision Handling

Example:


# 60. Free-Tier Bandwidth Protection

Render outbound bandwidth is a real constraint.

Therefore TPMC should avoid:

```text
download Telegram file
→ upload to Telegram
```

whenever forwarding/copying can achieve the desired result.

The application should not proxy music through Render.

# 79. Acceptance Criteria

TPMC is considered release-ready only if:

### Authentication

* [ ] Bot authenticates
* [ ] User session authenticates
* [ ] Unauthorized users rejected
* [ ] Secrets not logged

### Storage

* [ ] Channel accessible
* [ ] Audio messages detected
* [ ] Documents containing audio detected
* [ ] Missing captions handled

### Index

* [ ] Index builds
* [ ] Index survives application restart logically
* [ ] Index can be reconstructed from Telegram
* [ ] Duplicate messages do not corrupt index

### Search

* [ ] Exact tag search
* [ ] Artist search
* [ ] Album search
* [ ] Filename search
* [ ] Pagination

### Delivery

* [ ] Single track delivery
* [ ] Multiple track delivery
* [ ] Rate-limit handling
* [ ] Retry handling
* [ ] Failed track isolation
* [ ] Job cancellation

### Reliability

* [ ] Telegram reconnect
* [ ] Render restart
* [ ] Cold start
* [ ] Graceful shutdown
* [ ] No dependency on local persistent storage

### Security

* [ ] Private GitHub repository
* [ ] Secrets in Render environment
* [ ] `.env` ignored
* [ ] Session files ignored
* [ ] Authorization enforced

# 85. Antigravity Quality Gate

Before changing existing code, Antigravity must:

1. Inspect the repository.
2. Understand existing architecture.
3. Identify dependencies.
4. Identify stateful components.
5. Identify Telegram API boundaries.
6. Identify free-tier limitations.
7. Make the smallest safe architectural change.
8. Run tests.
9. Check logs.
10. Only then modify the next component.

Never rewrite working components unnecessarily.

# 86. Definition of "No Bugs"

The project must NOT use the phrase:

```text
zero bugs guaranteed
```

Instead use:

```text
production acceptance criteria
```

because external systems such as Telegram and Render can change behavior outside the application's control.

---

# 87. Definition of "Unlimited"

TPMC may conceptually use Telegram as a large personal media repository, but:

```text
Unlimited storage
≠
Unlimited compute
≠
Unlimited bandwidth
≠
Unlimited bot delivery
≠
Unlimited Render runtime
```

These must remain separate concepts.

---

# 88. Free-Tier Architecture

The correct goal is:

> **Zero mandatory infrastructure cost for a personal hobby deployment, subject to Telegram, Render, bandwidth, API and platform limits.**

Not:

> "Unlimited free production cloud."

Render itself describes Free instances as intended for testing, hobby projects and previews rather than production workloads.

# 91. Non-Goals

TPMC is NOT:

* a public music streaming service
* a multi-user SaaS
* a Spotify replacement
* a permanent CDN
* an unlimited-bandwidth proxy
* a guaranteed 24/7 service
* a commercial music distribution platform
* a backup system with independent redundancy

Telegram remains the primary storage dependency.

---

# 92. Final Engineering Rule

The single most important architectural rule is:

```text
NEVER make Render responsible for the existence of the music.
```

Render is disposable.

Telegram is the source of truth.

If Render disappears:

```text
Music remains safe in Telegram.
```

When Render returns:

```text
Reconnect
   ↓
Rebuild state
   ↓
Continue
```

That is the architecture that makes this project resilient rather than merely functional.
